## 4. 测试方法与判定规则

1. 模块测试：通过仓库依赖免费的断言框架验证协议、存储、命令分发和线程池。
2. 黑盒集成测试：经真实 Socket 发送请求，根据 RESP 响应及后续连接可用性判断结果。
3. 等价类和边界值：使用合法/非法端口、空值、不存在的键、精确上限及超限输入。
4. 协议传输测试：逐字节发送请求、一次发送多帧，检查响应内容与顺序。
5. 并发测试：四个客户端操作各自的键，校验每次 SET/GET；另由存储单元测试覆盖同一键的并发写入。
6. 兼容性测试：执行真实 redis-cli 的五个命令。

“通过”要求实际结果满足用例预期且执行成功；“部分验证”表示只有部分场景有证据；“未执行”不得计入通过率。TCP reset 只在已经读到 ERR 后的异常连接关闭检查中视为允许结果，不允许跳过错误响应检查。测试脚本的断言应保持启用，不使用 Python `-O`。

## 5. 测试执行过程

### 5.1 基础构建与兼容性验收

使用 GCC 完成 `build` 目录 Release 配置、构建和 CTest，4/4 测试通过。启动本次构建的服务器后，持续连接脚本完成 PING、SET、GET、EXISTS、DEL；真实 redis-cli 脚本也完成这五个命令，预期分别为 PONG、OK、software-engineering、1、1。

发送畸形输入 `!bad\r\n`，收到协议错误；随后重新运行持续连接测试通过。结束后停止测试服务器。

### 5.2 新目录 GCC 复现

```powershell
cmake -S . -B build-acceptance -G "MinGW Makefiles" -DCMAKE_BUILD_TYPE=Release
cmake --build build-acceptance --parallel 4
ctest --test-dir build-acceptance -C Release --output-on-failure
python build-acceptance/acceptance.py
```

配置、构建成功，CTest 4/4 通过。扩展脚本完成第 6 节所列网络及参数检查。新目录只说明同机新构建复现，不视为全新机器验收。

### 5.3 MSVC 复现

```powershell
cmake --fresh -S . -B build-msvc-acceptance -G "Visual Studio 17 2022" -A x64
cmake --build build-msvc-acceptance --config Release --parallel 4
ctest --test-dir build-msvc-acceptance -C Release --output-on-failure
python build-acceptance/acceptance.py build-msvc-acceptance/Release/mini_redis.exe
```

初次配置因环境变量重复键失败；规范化子进程环境后，通过归档的 `msvc.py` 包装脚本执行前三条命令成功。MSVC CTest 4/4 通过，同一扩展验收脚本在 MSVC 产物上全部通过。真实 redis-cli 验收仅在基础 GCC 产物上执行，不扩写为 MSVC 也执行了该客户端脚本。

### 5.4 清理与记录

扩展脚本在 `finally` 中终止自身启动的服务器并等待退出。该方式只用于测试清理，不能证明 Ctrl+C 优雅退出。构建产物保留在忽略目录；报告及文本证据归档在 `docs/reports/`。
